## 2. 重点项目分析

### 2.1 browser-use（借鉴最多）

- **核心机制**：DOM 提取所有可交互元素并编号，元素列表（文本）+ 标注截图发给 LLM，LLM 输出针对编号的动作 JSON；注册式动作系统；历史消息折叠。
- **验证结论**：该"编号元素 + 动作 JSON"接口对非 CUA 专训模型最友好，14B+ 模型即可工作（autofill 项目实测 qwen2.5:14b 可用，≤7B 容易误填）——与我们 35B 端点匹配。
- **不直接依赖的原因**：其提示词与抽象为通用浏览任务设计、体量大且演进快，表单场景只需其中子集；自研可将提示词全面中文化并针对简历表单做窄域优化，同时避免版本追赶。
- **具体借鉴**：`dom_extract.js` 的元素属性集合、可见性判定、动作 registry 模式、批量动作 + 页面变更即中断的执行策略。

### 2.2 Skyvern（架构范式出处）

- **Planner–Actor–Validator 循环**的量化收益（WebVoyager）：单 Actor 循环 ~45% → 加 Planner ~68.7% → 加 Validator 85.85%。印证任务拆分与显式校验是成功率的关键，而非单纯堆模型。
- 其他借鉴点：目标导向而非录制回放；登录/2FA 显式建模为需要人工的状态；结构化输出 schema 定义任务产出。
- AGPL-3.0，只借鉴思想不引用代码。

### 2.3 AIHawk（产品形态参考）

- 3 万 star 验证了"求职自动化桌面/本地软件"的真实需求；社区 PR 演进出的形态与本项目高度一致：FastAPI + 内嵌 SPA、应用内 LLM 提供商选择（Claude/OpenAI/Gemini/Ollama）、bot 生命周期管理（启停/暂停/会话统计）、申请历史仪表盘、WebSocket 实时进度。
- 教训借鉴：早期版本按平台（LinkedIn 等）写死流程导致维护崩溃、平台封禁与法律风险，最终仓库归档——**坚定本项目"泛化 + 用户审核提交 + 不做批量海投"的定位**。

### 2.4 Qwen-CUA / 纯视觉路线（保留为扩展点）

- 优势：不依赖 DOM，可操作桌面原生应用；Qwen-CUA 在 OSWorld-Verified 86.2 分。
- 不作为主路线的原因：需要 CUA 专训模型（397B-A17B MoE），我们的通用 35B 端点像素 grounding 不可靠；且简历场景 99% 在浏览器内，DOM 路线信息更充分、可回读校验。
- 落点：`drivers/base.py` 抽象出 `Driver` 接口，未来接入 CUA 模型时实现 `vision_desktop.py` 即可复用上层多智能体与档案体系。

## 3. 差异化定位

| 维度 | 现有方案 | AutoOffer |
| --- | --- | --- |
| 目标场景 | 通用浏览任务（browser-use/Skyvern）或海投（AIHawk） | 简历表单窄域深耕：区块级任务拆分、日期区间/级联等控件策略链、档案切片注入 |
| 模型要求 | 多依赖 GPT/Claude 级别或专有优化模型 | 面向自建 30B 级 OpenAI 兼容端点优化（短提示、编号接口、guided JSON） |
| 交付形态 | 库/平台/脚本 | 普通用户可安装的 Windows 桌面软件，应用内配置模型 |
| 中文场景 | 弱（学历/籍贯/政治面貌等中文简历特有字段无处理） | 中文提示词与中文简历字段体系原生支持 |
| 安全边界 | 部分方案自动提交甚至绕过风控 | 默认不提交、敏感动作门禁、不碰验证码 |
